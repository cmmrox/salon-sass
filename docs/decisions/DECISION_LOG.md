# Decision log

One entry per decision, newest last. An entry says what was decided and why, so that it is not
argued again without new information. Open product decisions (D-01 to D-13) are in the BRD,
section 14; when one is settled, record it here.

| No. | Date | Decision | Why |
| --- | --- | --- | --- |
| 001 | 2026-10-12 | A feature is something a salon or its customers can use, cutting across API, web and mobile. A stage is a part of it that QA can test on its own. Work is never divided by layer | The owner wants every feature releasable to customers and every stage testable by QA. Dividing by layer produces "features" nobody can use |
| 002 | 2026-10-12 | Three roles: lead, developer, QA. The developer and QA are separate agents, and the handoff between them is read from `stage.yaml` and the bug files | A check written from the same assumptions as the code agrees with the code. A file-based handoff works whether the roles run in Claude Code, Codex or both |
| 003 | 2026-10-12 | A stage QA pass runs that stage's automation only; a feature pass runs that feature's only; regression and smoke run only when the owner asks | The owner's explicit rule. Enforced by `qa/scripts/sdlc run`, which selects by scope |
| 004 | 2026-10-12 | Three skills (`salon-sdlc`, `salon-dev`, `salon-qa`) with real files under `.claude/skills/` and symlinks under `.agents/skills/` | Each role loads only its own guidance, and one copy cannot drift from another. Narrowed by decision 013: the skills hold process only |
| 005 | 2026-10-12 | Status lives only in `feature.yaml` and `stage.yaml`. `features/README.md` and `qa/coverage.md` are generated. `qa/scripts/sdlc validate` is the gate | Hand-kept status boards go stale; a gate that is a script cannot be talked around |
| 006 | 2026-10-12 | GitHub; `main` as trunk; one branch per stage named `{username}/{type}/{id}-{slug}`; Conventional Commits scoped to the stage; merge commits, not squashes | The owner's existing convention, with the stage id added for traceability. Merge commits keep developer and QA commits attributable |
| 007 | 2026-10-12 | Placeholder names until D-02 is decided: skill prefix `salon-`, Java base package `com.salonplatform`, npm scope `@salon`, app identifiers under `com.salonplatform` | The product has no name yet. Each placeholder is kept in one place so the rename is mechanical |
| 008 | 2026-10-12 | QA tooling: Playwright for browser and API tests, Maestro for the customer app, k6 for load and concurrency | One runner and one set of fixtures for web and API; Maestro and k6 are the lightest tools that test a real device and a real race |
| 009 | 2026-10-12 | The OpenAPI document is generated from the API's controllers and committed; the TypeScript client is generated from it; a drift check fails the build | One contract for web and mobile, with no hand-written copy to fall behind |
| 010 | 2026-10-12 | Release 1 is 16 features covering the BRD's 96 Release 1 requirements, each requirement owned by exactly one feature | Traceability from requirement to stage to test case, checked by the validator |
| 011 | 2026-10-12 | Every requirement change, and every QA suggestion the owner accepts, goes through a change request under `docs/changes/` | Requirements will arrive mid-flight; specs, cases and automation must change together |
| 012 | 2026-10-12 | Delivery order: the web application first (`M1-web`, F01 to F14), released, then the customer mobile app (`M2-mobile`, F15 and F16). Nothing under `apps/mobile` is built before then; F01 is web-only | The owner's decision. The booking site serves customers on their phones in the meantime, and the API is built so the app needs no backend rework. Recorded in `docs/ROADMAP.md`. Each feature carries a `milestone`; the portfolio shows a later milestone as waiting, and the validator refuses a feature that starts before the earlier milestone is released unless the owner's instruction is recorded in `started_early` |
| 013 | 2026-10-12 | Everything specific to this product lives under `docs/` (architecture, stack, repository structure, engineering rules, design standards, test plan, environments), indexed by `docs/README.md`. The three skills hold only how work is done and point to those documents; each stage's `spec.md` names the documents to read under "Read first"; each application folder has a short `AGENTS.md` doing the same. The lead owns the documents | The owner's decision, and the common practice. One home for each fact, so the skills cannot drift from the documents, and the same skills can be reused in another project. The validator checks the index and every pointer |
