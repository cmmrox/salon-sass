A caution on single-salon apps

Customers install few apps and are selective about adding one for a business they visit every six weeks. The research supports online booking strongly; it does not show that customers demand a separate app per salon. The booking site must therefore be a first-class channel, and the app must earn its place on the phone with things a web page cannot do as well: one-tap rebooking, push reminders at no message cost, a loyalty card, and saved payment details.

Where the platform should not compete

  • Lowest price: Fresha is already at LKR 1,190 per team member.
  • Feature count against products ten years old.
  • Consumer discovery: marketplaces own that.

Where it can win

  • Your brand, your customers. Own app, own domain, no marketplace, no commission.
  • Built for here. Rupee gateways, LANKAQR and cash recorded properly, WhatsApp-first messaging, Sinhala and Tamil, local public holidays, local support hours.
  • Honest costs. Flat pricing by location, message costs shown before sending.

7. Recommended solution approach

This section answers “what is the best way to build this kind of application”. It records the approach and the reasons, at the level a business decision needs; the solution design document will take it to implementation detail.

7.1 Solution overview

Why a modular monolith. The team is small and the domain is tightly connected: a booking touches catalogue, staff, payments and notifications in one transaction. One deployable with enforced internal module boundaries keeps transactions simple and operations cheap, and leaves the option to separate a module (notifications is the likely first) when load justifies it. Microservices at this stage would add cost without adding anything a salon would notice.

7.2 Multi-tenancy model

Shared schema, tenant column, row-level security | Logical, enforced by the database on every query | Lowest: one schema, one migration, one connection pool | Thousands of tenants | Recommended Schema per tenant | Stronger separation of tables | Every migration runs once per tenant; catalogue grows with every salon; connection routing by search_path | Hundreds, comfortably | Not justified here Database per tenant | Strongest | Highest: a database to provision, patch, back up and monitor per salon | Tens | Keep as a future option for a large chain that demands it

The user requirement is a single application and a single database with tenant configuration. The shared-schema model is that requirement in its most economical form, and it is how most small-business SaaS products are built. Its one weakness is that isolation depends on every query being filtered. The guardrails below remove that dependence on developer discipline.

Tenancy guardrails (binding on the solution design)

T-1 | Every tenant-owned table carries a non-null tenant_id. Platform tables (plans, tenants, operator users) are held separately and are not reachable with a tenant role. T-2 | Isolation is enforced twice. In the application, Hibernate’s @TenantId adds the tenant filter to every query and stamps every insert. In the database, a row-level security policy on each table compares tenant_id with a per-transaction setting, with FORCE ROW LEVEL SECURITY on, so a query that bypasses the ORM is still filtered. T-3 | The application connects with a role that does not own the tables and cannot bypass row-level security. Migrations run under a different role. T-4 | The tenant setting is applied per transaction (set_config(…, true)), never per session, so a pooled connection cannot carry one salon’s context into another salon’s request. T-5 | The tenant is derived on the server from the hostname or the signed token. A tenant identifier sent by the client is never trusted on its own; where both are present they must match. T-6 | Unique constraints, foreign keys and indexes include tenant_id. A reference to another tenant’s row is impossible by construction. T-7 | Background jobs run one tenant at a time with an explicit context. A job without a tenant context can read nothing. T-8 | Caches, file paths, search indexes and log entries are keyed or tagged by tenant. T-9 | An automated test suite attempts cross-tenant reads and writes through every API endpoint on every build. A failure blocks release. T-10 | Operator access to tenant data is a deliberate, logged, time-limited action (PLT-07), not a standing privilege.

Notes on virtual threads

  • Virtual threads suit this workload: most request time is spent waiting on the database, the payment gateway and messaging providers.
  • They move the bottleneck, they do not remove it. With no thread-pool ceiling, the database connection pool becomes the limit. Size it deliberately and put explicit concurrency limits and timeouts on calls to external providers.
  • Carry the tenant in a request-scoped or scoped value (scoped values are final in Java 25) and avoid designs that depend on thread-local state surviving in pooled threads.
  • Monitor for remaining pinning (native calls, some file I/O) using the JDK’s pinned-thread event during load testing.

7.6 Booking integrity

Double booking is the failure a salon will not forgive. Application checks alone cannot prevent two customers confirming the same time in the same instant. The database must refuse the second one.

  • A hold and a booking are the same kind of record in different states, so one rule covers both.
  • A PostgreSQL exclusion constraint forbids two active records for the same tenant and professional with overlapping time ranges. The losing request receives a clear “that time was just taken” response, as the prototype already words it.
  • Holds carry an expiry time. A scheduled job releases expired holds, and the availability calculation ignores them the moment they lapse.
  • Payment confirmation, hold conversion and notification scheduling happen in one transaction; the notification itself is sent afterwards from the outbox, so a messaging outage never loses or duplicates a booking.

7.7 Integrations

Payments

Money flow | Customer pays the salon directly through the salon’s own gateway merchant account. The platform stores each salon’s gateway credentials encrypted and never receives booking funds. The salon’s subscription is a separate charge from the platform to the salon. First gateway | PayHere. Published fees at the time of writing: Lite plan, no monthly fee, 3.30% per transaction with payment limits; Plus, LKR 3,990 a month and 2.99%; Premium, LKR 9,990 a month and 2.69%. Abstraction | A payment-provider interface in the backend so that further gateways (other local providers, or an international one for tenants abroad) are additions, not rewrites. Truth | A booking is confirmed only when the gateway’s server-to-server notification is received and its signature verified. A reconciliation job queries the gateway for any payment still pending after a short interval. This is the mechanism behind the prototype’s “verification in progress” state. In-salon payments | Cash, card terminal, bank transfer and LANKAQR are recorded as tender types at checkout. No terminal integration in R1. Card data | Never touches the platform. Hosted checkout or the gateway’s SDK keeps the platform out of card-data scope.

7.8 Environments and operations

  • Hosting. A single region close to Sri Lanka (Singapore or Mumbai are the usual choices) on a managed PostgreSQL service with point-in-time recovery. Provider and data-residency position are decision D-08.
  • Environments. Development, staging with a set of synthetic tenants, production. A demonstration tenant for sales.
  • Releases. Backend and web: continuous delivery with backward-compatible database migrations, since app versions in the field lag behind. Mobile: over-the-air for JavaScript changes, store releases in waves for native changes.
  • API compatibility. Versioned API; a minimum supported app version per tenant with a forced-update screen (APP-19), because old builds stay installed for months.
  • Backups and recovery. Tested restore, including restoring a single tenant’s data to a point in time.
