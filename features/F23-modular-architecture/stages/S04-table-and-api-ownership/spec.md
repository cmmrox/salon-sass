# F23-S04 Table and API ownership by module

## Objective

Every table and every API path has one declared owning module, and tests hold that: a module's
code and new migrations touch only its own tables, no foreign key crosses modules, every API
operation is tagged with its module, and the generated client is exported per module. Settings are
read only by the module that owns them. This is what lets a module's data and paths be moved
later, and what the web restructure (F23-S06) and module events (F23-S05) build on. No endpoint,
field or behaviour changes.

## Scope

API and the contracts package:

- **Ownership map.** One file, `apps/api/src/main/resources/module-ownership.yaml`, lists for each
  module its tables and its API path prefixes. Today's assignment: `identity` owns the `identity_*`
  tables and `/api/v1/identity`; `branding` owns `salon_brand` and `/api/v1/salon` (exactly that
  path); `shared` owns `audit_entry`, `outbox_message`, `scheduled_job` and `/api/v1/meta`;
  `platform` owns every other existing table and `/api/v1/operator`, `/api/v1/billing`,
  `/api/v1/exports`, `/api/v1/support`, `/api/v1/salon/entitlements`, `/api/v1/salon/invoices` and
  `/api/v1/salon/support-sessions`. A path belongs to the module with the longest matching prefix
  (decision 058).
- **Tests on the migrated database**, each with a fixture or a deliberate fault proving it fails:
  - every table in the application's schema is in the map exactly once, and every table in the map
    exists;
  - no foreign key joins tables of two modules, except `tenant_id` to `tenant`;
  - every table created by a migration numbered after this stage's last existing one carries its
    module's prefix (existing tables keep their names, CR-021 decision 4).
- **Tests on the code:**
  - the table names in a module's `@Table` annotations, JPQL and SQL string literals are its own
    tables (a scan of the compiled classes' string constants is acceptable), with `shared`'s own
    tables used only from `shared`;
  - every operation in the generated OpenAPI document has exactly one tag, which is the name of the
    module that owns its path by the map, and every path matches a prefix in the map.
- **Tags.** Controllers are tagged with their module's name (`identity`, `branding`, `platform`,
  `shared`), replacing the per-controller tags. The OpenAPI document changes in its tags only; no
  path, operation id, parameter, schema or field changes.
- **Per-module documents.** A springdoc `GroupedOpenApi` per module, selected by the map's
  prefixes; the committed merged document stays the contract.
- **Per-module client.** `packages/api-contracts` exports one entry per module
  (`@salon/api-contracts/identity`, `/branding`, `/platform`, `/shared`) through `exports`
  subpaths, each exposing only that module's paths and the schemas they use, generated by the
  existing contract script so that `pnpm contracts:check` covers them. The current root export keeps
  working until F23-S06 moves the web onto the module entries.
- **Settings.** No module reads another module's settings. `shared`'s settings keep their names
  (`salon.platform-domain`, `salon.database`, `salon.outbox`, `salon.jobs`); each business module
  reads only `salon.<module>.*`. Platform today reads `salon.identity.*` keys (`OperatorSecrets`,
  `ExportKey`); replace that with a mechanism that does not cross the boundary (for example a check
  in `shared` that every configured secret key is distinct, or identity confirming through a
  provided interface), keeping the security property those reads enforce. A test proves the
  property still holds.
- **Clean code** in everything touched; **documentation hand-back** in `handoff.notes`.

## Out of scope

- Renaming existing tables, moving tables into per-module schemas, or changing any path: deferred
  (CR-021 decision 4).
- Moving the web onto the per-module client entries: F23-S06.
- Edge routing per module: not built until a module is extracted.

## Acceptance criteria

Each criterion is one observable outcome that a test can pass or fail.

- AC-1: An integration test on the migrated database fails when a table is missing from the map,
  listed twice, or listed but absent, and passes for the application: every table has exactly one
  owning module. (NFR-22)
- AC-2: An integration test fails on a fixture foreign key between two modules' tables, and passes
  for the application: the only foreign keys across modules are `tenant_id` to `tenant`. (NFR-22)
- AC-3: A test fails when a fixture class in one module names another module's table in a JPQL or
  SQL literal or `@Table`, and passes for the application. (NFR-22)
- AC-4: A test fails when an operation is untagged, carries a tag other than its owning module's,
  or has a path matching no prefix in the map; it passes for the application, where every operation
  carries exactly one module tag. (NFR-22)
- AC-5: Apart from tags, the OpenAPI document is unchanged: a comparison of `docs/api/openapi.json`
  with `origin/main` with the `tags` removed from both shows no difference, and `pnpm
  contracts:check` passes. (NFR-18)
- AC-6: `@salon/api-contracts/<module>` resolves for each module, a TypeScript file importing a
  path of another module from it fails to type-check, and the existing root import still compiles
  in the web app (`pnpm -r typecheck` passes). (NFR-22)
- AC-7: No class of one module reads a setting under another module's prefix (a test or
  architecture rule fails on a fixture that does), and the property the removed cross-module reads
  protected still holds, proven by a test that fails when it is broken. (NFR-22)
- AC-8: Behaviour is unchanged: every test on the feature branch before this stage still passes with
  unchanged assertions; the web app builds and its tests pass; the local stack's operator console and
  salon workspace work as before. (NFR-18)

## Design notes

- Read the table list from the migrated test database (`information_schema` and `pg_catalog`), not
  by parsing migration files, so the test sees what Flyway actually produced, functions and all.
- The tag change is visible in the generated client only where tags are used; check what
  `openapi-typescript` emits and keep the generated `paths` keys and component names identical.
- The per-module client entries can be type-level filters over the generated `paths` (keys
  starting with the module's prefixes, longest prefix wins), so there is still one generated file.
- `/api/v1/salon` is owned by `branding` as an exact path, while three sub-paths belong to
  `platform`; this is the reason the map uses longest-prefix ownership rather than one segment per
  module.

## API and data changes

The OpenAPI document's operation tags change to module names (AC-5 proves nothing else changes).
No endpoint, field, table or migration changes. `packages/api-contracts` gains per-module exports.

## UI and UX

Not applicable for this stage.

## Risks and test focus

- **Contract drift beyond tags** (`api`): AC-5.
- **A security property lost with the settings change** (`security`): AC-7 must prove the property
  the cross-module key reads enforced (keys distinct, or whatever they guarded) still holds.
- **Ownership tests that check nothing** (`build`): each test needs its failing fixture or fault
  (AC-1 to AC-4, AC-7).
- **Web build broken by the contracts package change** (`build`): AC-6 and AC-8.
